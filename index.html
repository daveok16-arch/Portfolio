Case Study 1 — Intent Security Workbench: architecture that cannot fake findings

Problem

Security research across multiple bug-bounty platforms and blockchain ecosystems needs structure: scope discipline, verification state, provenance, and — critically — protection against fabricated or overstated findings.

Approach

I designed a modular monorepo where every subsystem enforces honesty by construction: findings move through a strict 10-state machine, artifacts get SHA-256 digests over raw bytes, engines report their real install status, and shell execution is confined to a sandbox that rejects compound commands and destructive verbs.

Implementation

TypeScript packages (core, orchestrator, evidence, source, agent-runtime), pluggable engine registry with real availability checks, Python FastAPI stub that honestly reports not_wired, a React/Vite research workbench UI (12 views), and a git-source-integrity engine running real host git operations.

Evidence

  • 88-test Vitest suite guarding the invariants (79 pass on a bare host; 9 real-tool tests truthfully report their missing tooling
  • Screenshots captured from the live dev server (dashboard and engine registry) and engine registry below
  • docs/: ARCHITECTURE, EVIDENCE_MODEL, SECURITY_MODEL, PHASES plus more

Result

A foundation that produces machine-verifiable evidence or nothing at all — designed to scale to real multi-program research in later phases.

What I learned

Anti-fabrication is an architectural property, not a policy: when validating a finding depends on authentic artifacts, the honest path is enforced by the state machine instead of by intentions.

Case Study 2 — Virtual Football: finding a real pricing edge, then proving it

Problem

A sportsbook streams virtual-football fixtures through a WebSocket inside an iframe. There was no documented API. I needed deterministic scheduled fixtures, 1X2 odds, standings, and resolved results — and eventually a way to know whether a prediction model has any real edge versus noise.

Approach

I attached to the GoldenRace iframe via Chrome DevTools Protocol sub-sessions and intercepted its WebSocket frames, normalizing them into league → week → fixtures. Then I built the prediction engine as a decoupled seam and, crucially, a rigorous validator before trusting any model.

Implementation

Node.js + Puppeteer CDP interception, NDJSON accumulation, Telegram delivery, and an engine contract (analyze() returning report, valueReport, summary, metrics). The validator computes Harville exacta probabilities from win probabilities, thresholds strategies with 95% Wilson confidence intervals, break-even tests, Brier scores, and a sample-size-gated PASS/FAIL verdict.

Evidence

  • n=156 races, 5,726 exacta pairs — PASS. At threshold odds×Harville > 0.93: ROI +433.9%, win rate 95% CI [2.78%,4.51%] vs break-even 0.53%
  • The same numbers appear in the repo commit history and validator source
  • Speculative tail (prod > 20–50) flagged or excluded — never recommended what cannot be validated

Result

A live exacta bot applying the confirmed edge with fractional-Kelly sizing, per-slate bankroll caps, and mutual-exclusivity-aware staking — built after, not before, the evidence existed.

What I learned

Sample-size gating to PASS is behavioural: the disciplined exclusion of thin-data tails is what keeps a backtest from turning into a mirage.

Research & Security

Security research, done responsibly.

My security work focuses on the craft that produces reliable findings: source-code inspection, vulnerability reasoning, reproducibility, and evidence discipline. No exploit weaponization, no fabricated results.

Source-code inspection

Workbench fixtures include deliberately secure-vs-vulnerable BOLA pairs; static engines (tree-sitter AST queries, semgrep, slither, angr, codeql seams) target these genuinely.

Vulnerability reasoning

Findings move through a strict 10-state machine: CANDIDATE → ANALYZING → VERIFICATION_REQUIRED → TESTING → REPRODUCED → VALIDATED → CONFIRMED — with transitions to verified states blocked unless linked evidence artifacts exist.

Reproducibility & provenance

Every artifact hashes its exact bytes with SHA-256; provenance chains record investigation → target → source snapshot → engine → command → timestamps. Tamper checks re-compute hashes at verify time.

Responsible practice

Engine containment avoids shell interpolation; the sandbox rejects compound commands, redirection into protected paths, and destructive verbs; external network scanning is restricted by design in Phase 0. No live exploits are published.

The workbench is at Phase 0 — foundational architecture for authorized research. It is explicitly designed to report UNAVAILABLE rather than fabricate success.
